# ডাটাবেস কনভেনশন

এই নথি একটাই প্রশ্নের উত্তর: **প্রতিটা টেবিলে কী কী থাকতেই হবে, আর কে তা নিশ্চিত করবে?**

উত্তর: কলামগুলোর তালিকা নিচে আছে, আর নিশ্চিত করে **ডাটাবেস নিজে** — অ্যাপ্লিকেশন কোড নয়।
১৫০+ টেবিলে হাতে কলাম কপি করলে কোথাও একটা বাদ পড়বেই। তাই তিনটি স্তর:

1. `core.ss_row_template` — ছাঁচ টেবিল। `LIKE ... INCLUDING ALL` দিয়ে কলাম কপি হয়।
2. `core.ss_apply()` — টেবিল বানানোর পর একবার ডাকতে হয়। ট্রিগার, RLS, ইনডেক্স ও অনুমতি বসায়।
3. `99_verify.sql` — CI-তে চলে। কোনো টেবিল কনভেনশনের বাইরে থাকলে **মাইগ্রেশন ব্যর্থ করে দেয়**।

---

## প্রাইমারি কী

সব প্রাইমারি কী `uuid`, ডিফল্ট `core.uuidv7()`।

**কেন integer auto-increment নয়:** অফলাইন-ফার্স্ট অ্যাপে মোবাইল নেট ছাড়া রেকর্ড তৈরি
করে, তখন সার্ভার সিকোয়েন্স পাওয়া যায় না। UUID ডিভাইসেই তৈরি হয়, কোলিশনের ভয় নেই।

**কেন v4 নয়, v7:** UUIDv7 এর প্রথম ৪৮ বিট ইউনিক্স মিলিসেকেন্ড, তাই কী গুলো সময়
অনুসারে সাজানো থাকে। B-tree ইনডেক্সে র‍্যান্ডম ইনসার্টের পেজ-স্প্লিট হয় না — বড়
টেবিলে v4 এর চেয়ে অনেক দ্রুত।

PostgreSQL 18 এ `uuidv7()` বিল্ট-ইন। `core.uuidv7()` ফাংশনটা PG 13–17 এর জন্য;
PG 18 এ গেলে বডি বদলে শুধু `select uuidv7()` করলেই হবে।

মানুষের পড়ার জন্য আলাদা সংকেত থাকে — `unit_code`, `tag_no`, `farm_code` — যেগুলো
টেন্যান্টভিত্তিক ইউনিক।

### নামকরণ: `_no` প্রত্যয়
প্রাইমারি ও ফরেন কী-তে `_no` প্রত্যয় (`organization_no`, `production_unit_no`)।
মান uuid, কিন্তু ERP-র প্রচলিত ভাষায় এটা "নম্বর"। সঙ্গতিই মুখ্য।

## টেন্যান্ট ও স্কোপ

| কলাম | কোথায় | কেন |
|---|---|---|
| `organization_no` | সব ব্যবসায়িক টেবিলে | টেন্যান্ট মূল। `COMPANY_NO` নয় — বাংলাদেশের বেশিরভাগ খামার কোম্পানি নয়, ব্যক্তিমালিকানা বা পারিবারিক অংশীদারি |
| `farm_no` | লেনদেন টেবিলে | এক মালিকের একাধিক খামার থাকে |
| `fiscal_year_no`, `period_no` | হিসাব টেবিলে (পরবর্তী ফেজ) | জুলাই–জুন অর্থবছর, পিরিয়ড লক |

প্রতিটা টেবিল `core.ss_table_registry` তে একটা **scope** নিয়ে নথিবদ্ধ:

| scope | মানে |
|---|---|
| `root` | টেবিলের প্রাইমারি কী-ই `organization_no` (শুধু `core.organization`) |
| `tenant` | `organization_no NOT NULL` — শুধু নিজের টেন্যান্টের সারি দেখা যায় |
| `shared` | `organization_no` NULL হতে পারে। NULL = গ্লোবাল মাস্টার ডেটা, সবাই পড়তে পারে; লিখতে পারে শুধু নিজের সারিতে |
| `system` | টেন্যান্ট কলাম নেই, RLS নেই (শুধু অবকাঠামো) |

`shared` স্কোপই "গ্লোবাল + টেন্যান্ট ওভাররাইড" প্যাটার্ন দেয়: ১১৬টি জাত সবাই পায়,
কিন্তু কোনো খামারি নিজের স্থানীয় ক্রস যোগ করলে সেটা শুধু তার।

## অডিট কলাম

`core.ss_row_template` থেকে কপি হয়, ট্রিগার বসায়:

| কলাম | কে বসায় | মন্তব্য |
|---|---|---|
| `ss_created_by` | ট্রিগার | `app.user_no` থেকে; না থাকলে সিস্টেম ব্যবহারকারী |
| `ss_created_time` | ট্রিগার | সার্ভার সময়, `timestamptz` (UTC) |
| `ss_modified_by` | ট্রিগার | |
| `ss_modified_time` | ট্রিগার | |
| `ss_row_version` | ট্রিগার | প্রতি UPDATE এ ১ বাড়ে — optimistic locking |
| `ss_active_flag` | অ্যাপ | মাস্টার ডেটা নিষ্ক্রিয় করা |
| `ss_deleted_flag` | অ্যাপ | সফট ডিলিট |
| `ss_deleted_by` / `ss_deleted_time` | ট্রিগার | flag বদলালে স্বয়ংক্রিয় |

### যা রাখা হয়নি, সচেতনভাবে

**`SS_UPDATE_BY` রাখা হয়নি।** `ss_modified_by` এর সাথে ডুপ্লিকেট। দুটো থাকলে ছয় মাস
পর কেউ জানবে না কোনটা আসল, আর অর্ধেক কোড একটাতে লিখবে, বাকি অর্ধেক অন্যটাতে।

**অডিট কলামে ফরেন কী দেওয়া হয়নি।** `ss_created_by` → `core.app_user` এর FK দিলে
(ক) প্রতিটা INSERT-এ একটা অতিরিক্ত যাচাই — উচ্চ-ভলিউম দৈনিক লগে ব্যয়বহুল,
(খ) ব্যবহারকারী মুছলে পুরো অডিট ইতিহাস আটকে যেত। পরিচয় রিপোর্টে JOIN দিয়ে মেলানো হয়।

`ss_created_time` স্থাপনের পর অপরিবর্তনীয় — ট্রিগার UPDATE-এ পুরোনো মানই ফিরিয়ে দেয়।

## অফলাইন সিঙ্ক

সাধারণ ERP-তে এগুলো থাকে না, কিন্তু গ্রামের খামারে নেট থাকে না — তাই লাগবে।

| কলাম | কাজ |
|---|---|
| `ss_client_uuid` | idempotency key। সিঙ্ক রিট্রাই হলে ডুপ্লিকেট সারি হবে না (partial unique index) |
| `ss_device_no` | কোন ডিভাইস থেকে এন্ট্রি। শ্রমিকরা ডিভাইস শেয়ার করে |
| `ss_device_time` | ডিভাইসের ঘড়ি। **গ্রামের ফোনের সময় প্রায়ই ভুল**, তাই এটা `ss_created_time` এর বিকল্প নয় — পাশাপাশি |
| `ss_sync_seq` | গ্লোবাল সিকোয়েন্স থেকে। ক্লায়েন্ট চায় "আমার শেষ দেখা seq এর পরের সব" |

প্রতিটা টেবিলে `(organization_no, ss_sync_seq)` ইনডেক্স আছে — `ss_apply()` বানিয়ে দেয়।

## Row Level Security

`organization_no` কলাম রাখাই যথেষ্ট নয়। `ss_apply()` প্রতিটা টেন্যান্ট টেবিলে
RLS চালু করে এবং চারটি পলিসি (select/insert/update/delete) বসায়।

অ্যাপ প্রতি কানেকশনে বসায়:

```sql
SET LOCAL app.organization_no = '...';
SET LOCAL app.user_no         = '...';
```

`SET LOCAL` ব্যবহার করুন — কানেকশন পুল থেকে অন্য টেন্যান্টের সেশনে মান লিক হওয়া আটকাতে।

**fail-closed:** `current_org_no()` NULL হলে `organization_no = NULL` → NULL → false।
কোনো সারিই দেখা যায় না। প্রসঙ্গ বসাতে ভুলে গেলে ফাঁকা ফলাফল আসে — অন্য কারো ডেটা আসে না।

**`FORCE ROW LEVEL SECURITY`** দেওয়া আছে, তাই টেবিলের মালিকও RLS মানে। কিন্তু
superuser সর্বদা বাইপাস করে — তাই:

- মাইগ্রেশন ও সিড: superuser দিয়ে
- রানটাইম: `farmerp_app` ভূমিকা দিয়ে, **কখনো superuser দিয়ে নয়**

`db/rls_test.sql` ঠিক এটাই পরীক্ষা করে — ভূমিকা বদলে। superuser দিয়ে RLS পরীক্ষা
করলে কিছুই প্রমাণ হয় না; এই ভুলটা খুব সাধারণ।

## অপরিবর্তনীয়তা

### টেন্যান্ট কলাম
`ss_tenant_guard_trigger` — একটা সারি কখনো এক খামার থেকে আরেক খামারে "সরে" যেতে পারে না।

### নির্দিষ্ট ব্যবসায়িক ফিল্ড
`core.ss_immutable_columns_trigger()` পুনর্ব্যবহারযোগ্য:

```sql
create trigger pu_immutable_bu before update on prod.production_unit
  for each row execute function core.ss_immutable_columns_trigger(
    'tracking_mode', 'species_no', 'farm_no', 'opened_on');
```

একটা ব্যাচ "ব্রয়লার" হিসেবে শুরু করে মাঝপথে "লেয়ার" হয়ে গেলে আগের সব হিসাব
অর্থহীন। ভুল হলে ইউনিট বাতিল করে নতুন খুলতে হবে।

### অ্যাপেন্ড-অনলি টেবিল
`ss_apply(..., p_append_only => true)` দিলে UPDATE ও DELETE সম্পূর্ণ নিষিদ্ধ।
`prod.unit_movement` এমন — ভুল হলে উল্টো চলাচল (reversal) দিতে হয়, ঠিক যেমন
হিসাবের খাতায় কাটাকুটি করা হয় না।

## এক সত্য, এক জায়গা

স্কিমার সবচেয়ে গুরুত্বপূর্ণ নীতি, এবং যেটা সবচেয়ে বেশি লঙ্ঘিত হয়:

> **যে সংখ্যা যোগফল থেকে পাওয়া যায়, সেটা কলামে রাখা হয় না।**

তাই ইচ্ছাকৃতভাবে **নেই**:

- `production_unit.current_qty` — চলাচলের যোগফল থেকে আসে (`prod.v_unit_balance`)
- `production_unit.opening_qty` — `OPENING`/`DOC_RECEIPT` চলাচল থেকে আসে
- `flock.doc_count` — একই কারণে
- দৈনিক লগে মড়কের ঘর — `prod.unit_movement` থেকে আসে; ডাটাবেস বসাতেই দেয় না

কারণ একটাই: দুই জায়গায় রাখলে একদিন অমিল হবে (ট্রিগার মিস, সমকালীন আপডেট,
ব্যাকডেটেড সংশোধন)। তখন খামারি জিজ্ঞেস করবে "লগে ৫টা মরেছে, খাতায় ৩টা — কোনটা সত্য?"
— আর সেই প্রশ্নের উত্তর দেওয়া যায় না।

`floor_area_sqft` একটা generated column — `length_ft * width_ft`। একই নীতি।

## ত্রুটি বার্তা

সব ব্যবসায়িক ত্রুটি বাংলায়, উপযুক্ত SQLSTATE সহ:

| অবস্থা | errcode |
|---|---|
| ব্যবসায়িক নিয়ম ভঙ্গ | `check_violation` |
| অ্যাপেন্ড-অনলি / লক করা সারি | `restrict_violation` |
| বাধ্যতামূলক তথ্য নেই | `not_null_violation` |
| তারিখ/পরিসর ছেদ | `exclusion_violation` |

অ্যাপ errcode দেখে আচরণ ঠিক করবে, বার্তার লেখা পড়ে নয়।

### যাচাই
```bash
cd farm-erp/db && ./build.sh
```
শূন্য থেকে ডাটাবেস বানায় → স্কিমা → সিড → কনভেনশন যাচাই → স্মোক টেস্ট → RLS টেস্ট।
যেকোনো ধাপ ব্যর্থ হলে থামে। CI-তে এটাই চলবে।

- `schema/99_verify.sql` — ৩৬টি টেবিলে অডিট কলাম, ট্রিগার, RLS, পলিসি, uuid PK আছে কি না
- `smoke_test.sql` — একটা বাস্তব সমন্বিত খামার (৫ ইউনিট, ৫ প্রজাতি) বানিয়ে ৯ বিভাগে যাচাই
- `feed_test.sql` — গুদাম ও রেশন, ১৩ বিভাগে যাচাই (সর্বোত্তমতা, অসম্ভবতা, ভারিত গড়, ঋণাত্মক স্টক, লট, মেয়াদ, তালাবদ্ধ ফরমুলা, ইউরিয়া)
- `rls_test.sql` — ভূমিকা বদলে টেন্যান্ট পৃথকীকরণ (superuser দিয়ে নয়)

## অমীমাংসিত সিদ্ধান্ত

1. **অ্যাপ্লিকেশন স্ট্যাক** — অফলাইন-ফার্স্ট বাধ্যতামূলক। Flutter + SQLite + সিঙ্ক,
   নাকি React PWA + IndexedDB? স্কিমা দুটোর জন্যই প্রস্তুত (UUIDv7 + `ss_sync_seq` +
   `ss_client_uuid`), কিন্তু সিদ্ধান্ত নিতে হবে।
2. **মালিকানা** — নিজের খামার নাকি বহু খামারির SaaS? বর্তমান স্কিমা SaaS-সক্ষম
   (RLS সহ multi-tenant), যা single-tenant হিসেবেও চলে। তাই এই সিদ্ধান্ত পিছিয়ে
   দেওয়া নিরাপদ ছিল — কিন্তু মূল্য নির্ধারণ ও অনবোর্ডিংয়ে লাগবে।
3. **মাইগ্রেশন।** এখন স্কিমা ফাইলগুলো "শূন্য থেকে বিল্ড" — `build.sh` প্রতিবার
   ডাটাবেস মুছে নতুন বানায়। ডেভেলপমেন্টে এটাই সবচেয়ে পরিষ্কার, কিন্তু প্রথম
   খামারে বসানোর আগে ক্রমবর্ধমান মাইগ্রেশন (sqitch, flyway বা নিজের সংস্করণ
   টেবিল) দরকার হবে — নইলে আপগ্রেডে ডেটা হারাবে।
4. **জাতের মানদণ্ড কার্ভ** — `master.breed_standard` কাঠামো তৈরি, ডেটা নেই।
   কব/রস/হাই-লাইনের প্রকাশিত কার্ভ বসানো যায়, কিন্তু কয়েক ব্যাচ পরে **খামারির
   নিজের বাস্তব ফলনই বেশি নির্ভরযোগ্য মানদণ্ড** হবে।
